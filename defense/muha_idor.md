# muha — IDOR в выдаче «пропуска» (permit) → чтение чужой памяти/флага

> Сервис реального бокса (не из тренировочного `services/`). Исходник живёт на боксе в
> `/opt/services/muha/` (Python/Flask, свой `docker compose`). Этот файл — разбор дыры и
> **SLA-безопасный** патч. Точные имена полей/колонок/функций подставь из `app.py`.

## Суть (в двух словах)

`POST /api/coupons` подписывает HMAC-«пропуск» (permit) на **любой** `object_id`, который
пришёл от клиента, **не проверяя, что этот объект принадлежит вызывающему**. А
`POST /api/memories/<mid>/read` принимает такой пропуск, сверяет HMAC и расшифровывает
содержимое памяти `mid`. Чекер кладёт флаг в «память». Значит:

> любой зарегистрированный игрок подписывает пропуск на `object_id = <mid чужой памяти>` и
> читает чужой флаг. Это **confused deputy / BOLA (object-level authz)** — сервер выступает
> «запутанным замом» и выдаёт мандат на чужой ресурс.

flag_id (публичный, из attack_data) для muha — почти наверняка и есть `mid` памяти с флагом,
т.е. атакующему даже угадывать ничего не надо.

## Цепочка атаки (для понимания, НЕ для фермы — это раздел защиты)

```
register/login                       # получили свою сессию
POST /api/coupons  {object_id: MID}  # MID = чужая память (= flag_id цели); сервер подписал permit
POST /api/memories/MID/read {permit} # HMAC валиден → сервер расшифровал и отдал чужой флаг
```

Корень: **авторизация на доступ к объекту не проверяется ни при выдаче пропуска, ни при
погашении.** HMAC лишь подтверждает «сервер это подписал», а не «тебе можно».

## Патч (главный, SLA-безопасный): проверка владения ПРИ ВЫДАЧЕ пропуска

Чини в `POST /api/coupons`: прежде чем подписать permit на `object_id`, убедись, что текущий
аутентифицированный пользователь **владеет** этим объектом (или он в его share-листе). Не
владеет → `403`, ничего не подписываем.

Почему именно при выдаче, а не только при чтении — см. «SLA-ловушку» ниже: легальный флоу
«поделиться памятью» это владелец, который чеканит пропуск на **свою** память; атака отличается
тем, что просит пропуск на **чужую**. Проверка владения на выдаче рубит атаку и **не трогает**
легальный шэринг.

Шаблон (Flask; подставь реальные имена — `current_user`, модель памяти, поле владельца):

```python
@app.post("/api/coupons")
def issue_coupon():
    user = require_auth()                      # как в сервисе: сессия/токен → текущий юзер
    object_id = request.json["object_id"]

    mem = Memory.query.get(object_id)          # найди объект (память), на который просят пропуск
    if mem is None:
        abort(404)
    # ГЛАВНАЯ СТРОКА: пропуск выдаём только владельцу (или тому, кому владелец его расшарил)
    if mem.owner_id != user.id and user.id not in getattr(mem, "shared_with", ()):
        abort(403)                             # не твой объект — пропуск не подписываем

    # дальше — как было, подпись permit; желательно привязать к юзеру и сроку (см. ниже)
    return {"permit": sign_permit(object_id, user.id)}
```

## Усиление (defense-in-depth, по возможности)

1. **Привяжи пропуск к субъекту и сроку.** Подписывай не только `object_id`, а
   `f"{object_id}|{user.id}|{exp}"`, и при погашении пересчитывай HMAC с **текущим**
   пользователем и проверяй `exp`. Тогда пропуск, выданный одному, нельзя переиграть другим,
   и его нельзя «дотюнить».

   ```python
   def sign_permit(object_id, uid, ttl=120):
       exp = int(time.time()) + ttl
       msg = f"{object_id}|{uid}|{exp}".encode()
       mac = hmac.new(PERMIT_SECRET, msg, hashlib.sha256).hexdigest()
       return f"{object_id}.{uid}.{exp}.{mac}"

   def verify_permit(token, object_id, uid):
       try:
           oid, tuid, exp, mac = token.split(".")
       except ValueError:
           return False
       if oid != str(object_id) or tuid != str(uid):   # пропуск именно этого юзера на этот объект
           return False
       if int(exp) < time.time():
           return False
       good = hmac.new(PERMIT_SECRET, f"{oid}.{tuid}.{exp}".encode().replace(b".", b"|"),
                       hashlib.sha256).hexdigest()
       return hmac.compare_digest(mac, good)            # всегда constant-time сравнение
   ```

2. **Проверка владения ПРИ ЧТЕНИИ** (`/api/memories/<mid>/read`) — только если чекер читает
   флаг **тем же** владельцем (см. ниже). Иначе сломает SLA. Если привязал пропуск к юзеру (п.1),
   то строгая owner-only проверка на чтении уже избыточна для блокировки атаки.

## ⚠️ SLA-ловушка — проверь, ЧТО делает чекер, прежде чем трогать путь чтения

Правило A&D: закрыть дыру, **не уронив то, что проверяет чекер** (иначе минус defense-очки).
Критичный вопрос: чекер в своём `get` читает флаг **тем же** юзером, что положил, или **другим**
через пропуск (проверяя фичу шэринга)?

- **(S1) тем же владельцем** → безопасна и проверка на выдаче, и owner-only на чтении.
- **(S2) другим юзером по пропуску** → owner-only **на чтении** сломает чекер (его легальный
  `get` — не владелец). А вот **проверка владения на выдаче** безопасна и здесь: пропуск чеканит
  владелец на свою память, затем передаёт — выдача проходит; атакующий просит пропуск на чужое —
  выдача рубится.

Вывод: **проверка владения на ВЫДАЧЕ безопасна в обоих случаях** — это и есть главный патч.
Строгую owner-проверку на чтении добавляй, только если убедился, что это S1.

Как проверить на боксе (прочитать чекер muha — это НЕ сервис, его можно читать):

```bash
# на боксе найди чекер muha и посмотри его get(): создаёт ли он нового юзера / логинится ли
# под другим перед чтением флага
find /opt/services/muha / -iname '*checker*' 2>/dev/null
grep -nEi 'def (get|put|check)|register|login|coupon|permit|/read|object_id' <путь_к_чекеру>
```

Если `get` не регистрирует нового юзера и читает под тем, кто клал → S1 (можно и owner-only на
чтении). Если регистрирует/логинится другим и использует пропуск → S2 (только проверка на выдаче).

## Почему filter_proxy здесь плохо помогает

`defense/filter_proxy.py` режет по **байтовой сигнатуре** payload'а. Здесь атака и легальный
запрос отличаются только **значением** `object_id` (свой mid против чужого) — по байтам их не
разделить. Сетевой фильтр эту IDOR чисто не закроет.

Единственный сетевой времянка-вариант (рискованный): резать `/api/coupons` целиком, **если**
чекер им не пользуется (это как раз и выясняет grep выше). Если пользуется — упадёт SLA. Поэтому
здесь **обязателен код-патч**, а не прокси.

# muha — ещё ДВА пути кражи флага через `/api/memories/<mid>/capsule` (НЕ закрыты в текущем app.py)

> ⚠️ **ВАЖНО для нашего бокса.** Присланный `app.py` (MUHA_A1.PY) уже чинит купон-IDOR выше
> (Баг A), **но** `capsule()` отдаёт сырые крипто-поля ЛЮБОЙ памяти без проверки владельца, а это
> открывает ещё два независимых пути чтения чужого флага. Оба **проверены эксплойтом на копии
> нашего же app.py** — наш бокс сейчас течёт. Это ровно тот «затёртый фикс тиммейта», про который
> писалось в заметке по гонке патчей: owner-check в `capsule()` снова отсутствует.

Эндпоинт:

```python
@app.get("/api/memories/<mid>/capsule")
@authenticated
def capsule(mid):
    row = db().execute("SELECT * FROM memories WHERE id=?", (mid,)).fetchone()
    if row is None: return fail("Воспоминание не найдено", 404)
    ct = bytes(row["ciphertext"])
    return jsonify(..., nonce=b64(row["nonce"]), ciphertext=..., tag=..., archive=row["archive"], ...)
    #            ^^^ ОТДАЁТ nonce + GCM-ciphertext + CBC-archive ЧУЖОЙ памяти, владельца не проверяет
```

Флаг лежит в `content` памяти, зашифрованном двумя способами сразу: **AES-GCM** на пер-мухином
`brain_key` (поле `ciphertext`) и **AES-CBC** на общем для процесса `archive_key` (поле `archive`).
capsule раздаёт оба — и оба можно расшифровать без ключа.

## Путь B — повтор nonce в AES-GCM (clone + capsule). Быстрый, ~20–140 мс. ПОДТВЕРЖДЁН

Цепочка (понимание; это раздел защиты):

```
GET  /api/memories/<чужой mid>/capsule      # nonce N (=counter жертвы) и ciphertext C2
POST /api/flies/<чужая_муха>/clone {revision:N}   # clone БЕЗ owner-check копирует brain_key, counter=N
POST /api/flies/<клон>/memories {content:"A"*len(C2)}   # наша память шифруется тем же (brain_key, nonce=N)
GET  /api/memories/<наш mid>/capsule         # наш ciphertext C1
# keystream KS = ("A"*L) XOR C1 ; флаг жертвы = C2 XOR KS     (классический two-time-pad)
```

Корень — **три вещи вместе**: (1) nonce GCM = `fly["counter"]` (предсказуемый и управляемый),
(2) `clone()` копирует `brain_key` в муху атакующего **без проверки владельца** и даёт задать
`revision`=counter, (3) `capsule()` без owner-check отдаёт чужой `ciphertext`+`nonce`. Любая из
починок рвёт цепочку.

**Патч (SLA-безопасный, проверено):** генерировать nonce СЛУЧАЙНО на каждую память, а не из счётчика:

```python
# было:  nonce = fly["counter"].to_bytes(12, "big")
nonce = secrets.token_bytes(12)        # хранится в row["nonce"], расшифровка читает его же → SLA цел
```

Проверено на копии app.py: владелец по-прежнему читает свою память (`read` → `200`, контент на месте),
а Path B перестаёт воровать даже при всё ещё открытом `capsule`. `secrets` уже импортирован.

## Путь C — CBC padding-oracle на `/api/archives/preview` (общий archive_key). Медленный, но реальный. ПОДТВЕРЖДЁН

`preview()` расшифровывает присланный `archive` общим `archive_key` и отвечает **разными кодами на
разных стадиях**: `422` только при плохом PKCS7-паддинге, `400` при неразобранном JSON, `403` при
чужом владельце, `200` своему. Это классический **padding oracle** → можно побайтово расшифровать
`archive` (а в нём — `content` = флаг) вообще без ключа, имея лишь чужой `archive` из `capsule`.
Проверено: на реальном чужом `archive` порча последнего байта → `422`, порча среднего блока → `400`,
нетронутый → `403` (три различимых ответа = оракул есть).

**Патчи (любой из двух):**
1. **owner-check в `capsule()`** (главный, бьёт сразу B и C — без чужого `archive`/`ciphertext`
   оба пути мертвы):
   ```python
   fly = get_fly(row["fly_id"])
   if fly["owner"] != g.user["id"]:
       return fail("Это чужое сознание", 403)
   ```
   Проверено: бьёт и B, и C, своя память читается. **SLA-оговорка:** убедись, что чекер вызывает
   `capsule` только своим владельцем (почти наверняка так — это «отдай крипто-капсулу МОЕЙ памяти»).
2. если трогать `capsule` боязно — **убери оракул**: один и тот же код/тело ответа для всех ошибок
   `preview` (unpad / json / owner), например всё `400 "Мозг не распознал воспоминание"`. Легальный
   предпросмотр своего `archive` (`200`) не страдает.

## Рекомендация по нашему боксу (минимум)

Применить **все три** независимые починки (они дёшевы и не конфликтуют):
`capsule` owner-check  +  случайный GCM-nonce  +  (опц.) единый код ошибки `preview`.
Тогда бокс закрыт против A (уже сделано), B и C. После — `docker compose up -d --build`, бэкап как
обычно (`cp app.py app.py.bak`). Эксплойт-двойник для самопроверки: `farm/sploits/muha.py`
(`python farm/sploits/muha.py 10.60.7.2 8000 <свой mid>` до патча крадёт, после — пусто).
