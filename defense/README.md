# defense/ — защита (патч-луп)

В A&D защита = закрыть у себя ту же дыру, **не уронив SLA**. Патч, который чинит баг, но ломает
то, что проверяет чекер, всё равно теряет очки. Поэтому после каждой правки проверяй **обе**
половины сразу.

## Валидатор патча

```bash
python defense/verify.py <service> [host] [port]
# по умолчанию — твой бокс team1 на локальном стенде (web:9301 crypto:9401 depot:9501)
# на боевой: python defense/verify.py web 10.60.1.2 5001
```
Он кладёт свежий флаг чекером, проверяет `put/get/check` (жив ли сервис = SLA) и запускает
эталонный эксплойт (крадётся ли флаг). Вывод:
- `SLA: OK` + `VULN: blocked` → **GOOD PATCH** (так и надо);
- `SLA: OK` + `VULN: STILL EXPLOITABLE` → патч не закрыл дыру, чини дальше;
- `SLA: BROKEN` → патч (или краш) сломал сервис — ты теряешь defense-очки, чини функциональность.

Проверено на стенде: непропатченный `web` → `SLA OK, STILL EXPLOITABLE`; после параметризации
запроса → `SLA OK, blocked` (эксплойт возвращает 0 флагов).

## Цикл защиты (локально)
1. Найди дыру у себя (разбор — `services/<svc>/solution.md`).
2. Почини `services/<svc>/app.py`.
3. `python defense/verify.py <svc>` (против своего бокса). Добивайся `GOOD PATCH`.
4. Перезапусти стенд (`Ctrl+C` → `python run_local.py`), чтобы правка поехала, и глянь скорборд.

## Разведка по трафику — `trafmon.py`

На своём боксе снимаешь трафик и ищешь, какой входящий запрос вызвал **выдачу флага** — это и
есть чужой эксплойт. Чинишь именно его, а сам запрос **переигрываешь в атаку** против других.

```bash
# на боксе:
sudo tcpdump -i any -s0 -w cap.pcap tcp
# разбор (classic pcap; pcapng -> tshark -F pcap -r in.pcapng -w cap.pcap):
python defense/trafmon.py cap.pcap --service-ports 5001,5002,5003 --exclude-ip <checker_ip> \
       --save-exploits exploits_from_traffic
```
Показывает: какие IP вытащили сколько флагов из каждого сервиса и **байты запроса-эксплойта**
(с `--save-exploits` — сохранит их на диск, чтобы переиграть). `--exclude-ip` — убрать чекер,
чтобы его легальные `get` не мешали. Сам парсит pcap (Ethernet / Linux SLL/SLL2 / raw IP),
зависимостей нет.

> Проверено: на тестовом pcap нашёл атакующего и показал его UNION-запрос, чекер отфильтровал.

## Автоопределение чекера + живой слушатель — `checkerwatch.py`

`trafmon.py` требует вручную указать `--exclude-ip <checker>`. `checkerwatch.py` **сам**
находит чекера в начале раунда, **запоминает** его и дальше слушает трафик вживую, помечая
атакующих.

Как отличает чекера от атакующих (надёжно): **флаг в c2s** (клиент→сервис) бывает только у
чекера — он *кладёт* флаг (`put`); атакующий флаг только *вытаскивает*, поэтому у него флаг в
**s2c** (сервис→клиент), а в запросе флага нет. Отсюда: `флаг в c2s ⇒ это чекер` (его IP
пишется в `defense/checker.json` и переживает перезапуск), `флаг в s2c у не-чекера ⇒ атака`
(байты запроса сохраняются на реплей). Это обходит ловушку «чекер тоже вытаскивает флаги своим
`get`» — по `get` его не спутать с атакующим, потому что он опознан по `put`.

```bash
# вживую на боксе в начале тест-раунда (Linux, нужен tcpdump + root):
sudo python3 defense/checkerwatch.py --service-ports 5001,5002,5003 \
     --my-ip 10.60.1.2 --save-exploits defense/live_exploits
# -> через тик-другой: "CHECKER IDENTIFIED: <ip>", далее "[ATTACK] <ip> -> :порт ..."

# офлайн по готовому pcap (где угодно, без root):
python defense/checkerwatch.py --pcap cap.pcap --service-ports 5001,5002,5003
```

Найденного чекера сразу можно отдать в `trafmon.py` как `--exclude-ip`:
```bash
python defense/trafmon.py cap.pcap --service-ports 5001,5002,5003 \
  --exclude-ip "$(python -c "import json;print(json.load(open('defense/checker.json'))['checker_ips'][0])")"
```

> ⚠️ Запустить можно только когда идёт трафик (во время раунда) — заранее «вычислить» чекера
> не из чего. Проверено на синтетическом pcap: чекер опознан и запомнён несмотря на его легальные
> `get`; два атакующих помечены, их запросы (UNION SELECT и path traversal) сохранены на реплей.

## Быстрый митигейт — `filter_proxy.py`

Пока нет полного патча — временно режешь конкретную сигнатуру payload'а прокси-фильтром перед
сервисом. Работает и для HTTP, и для сырого TCP (матчит по байтам).

```bash
# сервис уводишь на внутренний порт, фильтр ставишь на публичный
python defense/filter_proxy.py --listen 0.0.0.0:5001 --target 127.0.0.1:15001 \
       --block-re "(?i)union(\+|%20|\s)+select" --block-re "\.\./"
```
Соединения с совпавшей сигнатурой рубятся, остальное (включая трафик чекера) проходит. Держи
сигнатуры **узкими** и следи за SLA.

> Проверено: SLA-трафик проходит сквозь фильтр (`check/get` OK), эксплойт — рубится (0 флагов),
> а напрямую сервис ещё уязвим — то есть это чистый митигейт, не замена патчу (payload можно
> видоизменить). Полноценно чини `solution.md`-патчем + `verify.py`.

## Патч без простоя
Правь аккуратно: параметризация запросов, рандомный nonce, санитизация путей/ключей, нормальный
HMAC вместо самодельной подписи. Эталонные фиксы — в `services/<svc>/solution.md`.

> Нельзя «защититься» фаерволом по IP: к твоим сервисам должен ходить и чекер, и соперники —
> заблокируешь чекер → упадёт SLA. Основная защита = правильный патч.
