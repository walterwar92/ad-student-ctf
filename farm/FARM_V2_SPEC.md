# FARM v2 — полный спец: безотказная, умная, наблюдаемая ферма + GUI

> Статус: **черновик на обсуждение**. Это спецификация апгрейда `farm/` с нынешней
> версии (v1) до v2. Цель — максимально **безотказная** (ни один флаг не теряется),
> **умная** (сама подстраивает темп, переживает сбои, прячет сломанные эксплойты) и
> **наблюдаемая/управляемая** (живой GUI с контролем на лету) система.
>
> Контекст площадки — ForcAD, см. [../RECON.md](../RECON.md) и [../ARCHITECTURE.md](../ARCHITECTURE.md).
> Боевой пресет — [config.forcad.py](config.forcad.py). Интерфейс эксплойта заморожен:
> `exploit(host, port, flag_id) -> list[str]`.

---

## 0. Принципы (чем v2 отличается от v1)

1. **Decoupled submit.** Воровство и сдача флагов — разные независимые циклы. Сдача идёт
   по своему расписанию (token-bucket под лимит жюри), а не «в конце раунда». Медленный
   эксплойт больше не задерживает сдачу уже украденного.
2. **Persistence-first.** Любой флаг, попавший в поле зрения, мгновенно в SQLite.
   Падение процесса / Ctrl+C / перезапуск — очередь не теряется и не пересдаётся.
3. **Fail-safe defaults.** Любой внешний сбой (attack-data недоступна, жюри лежит,
   эксплойт завис) деградирует в безопасное поведение, а не в потерю флагов или спам.
4. **Zero new deps на боевом боксе.** Ядро и GUI — **только stdlib** (на тест-дне PyPI
   недоступен, Flask может не стоять). GUI на `http.server`, графики — инлайновый
   vanilla-JS, **без CDN** (атакующий бокс часто без интернета, только игровой VPN).
5. **Hot everything.** Эксплойты, цели, сервисы, темп сдачи, пауза — меняются на лету
   через GUI/файлы **без перезапуска**.
6. **Backward compatible.** Замороженный интерфейс эксплойта, форма конфига и CLI-флаги
   v1 продолжают работать. v2 = надстройка, старые `config.py`/`config.forcad.py` валидны.

## 1. Нынешнее состояние (v1) и его слабые места

Модули сейчас: `farm.py` (CLI/loop), `runner.py` (раунд), `submitters.py` (HTTP/TCP +
классификация вердикта), `store.py` (SQLite: pending/accepted/dropped + дедуп),
`attackdata.py` (fetch+normalize), `targets.py`, `util.py`, `sploits/`.

| # | Слабое место v1 | Чем грозит на игре | Решение в v2 |
|---|---|---|---|
| 1 | Сдача привязана к концу раунда (`_submit_pending` синхронно) | Медленные эксплойты тормозят сдачу свежих флагов → TOO_OLD | §3.5 отдельный submit-loop |
| 2 | Нет TTL у pending-флагов | Протухшие флаги сдаются вечно, жгут лимит жюри | §3.2 TTL + авто-expire |
| 3 | Нет лимита попыток/бэкоффа | `unknown`/`resubmit` ретраятся каждый раунд бесконечно | §3.2 `tries`/`next_try`, backoff |
| 4 | Таймаут эксплойта «advisory» (не форсится) | Эксплойт без своего таймаута навсегда занимает воркер | §3.3 жёсткий таймаут future + опц. subprocess |
| 5 | Эксплойты кешируются, нет hot-reload | Правка эксплойта в игре требует перезапуска фермы | §3.3 reload по mtime + кнопка в GUI |
| 6 | Грубый `sleep` между сдачами | Не знает реальный flags/min лимит → либо медленно, либо бан | §3.5 token-bucket + авто-тюнинг (AIMD) |
| 7 | Сдача строго oldest-first | У края TTL старые флаги чаще TOO_OLD | §3.5 настраиваемый порядок, newest-first у лимита |
| 8 | Attack-data тянется каждый раунд, при ошибке → `{}` | Фетч упал → (from_attackdata) не атакуем никого | §3.4 кеш last-good + свой цикл |
| 9 | Наблюдаемость — только логи | В горячке игры не видно, что работает, а что встало | §3.8 GUI-дашборд, §3.10 события |
| 10 | Нет управления на лету | Нельзя выключить сломанный эксплойт/цель без рестарта | §3.7 runtime-state, §3.8 контролы |
| 11 | Конфиг читается только на старте | Смена round/темпа/сервиса = рестарт | §3.7 hot-reload безопасного подмножества |
| 12 | Вердикт = regex по ответу, `unknown`→retry | Молчаливый accept → вечный ресабмит → дубликаты | §3.6 ForcAD `status`-bool + калибровка |
| 13 | Один процесс, одна машина | Тиммейты не могут лить флаги в общий сабмиттер | §3.9 клиент-сервер (опц., фаза 5) |
| 14 | `known()` под глобальным локом в горячем цикле | 20 воркеров дерутся за лок на каждый флаг-кандидат | §3.2 батч-дедуп, индексы |
| 15 | Нет глобального бэкоффа при «game not started» | Ферма молотит жюри впустую | §3.5 глобальная пауза сдачи по сигналу |

Что в v1 **хорошо** и сохраняем: SQLite-дедуп и переживание рестарта; плагинная модель
эксплойтов с замороженным интерфейсом; stdlib-only ядро; HTTP/TCP-сабмиттеры; пресеты
attack-data (teamservice/forcad/custom); `--dry-run`.

## 2. Целевая архитектура

Пять независимых, слабосвязанных единиц вокруг одной SQLite-БД как шины состояния:

```
                         farm/farm_state.db  (единый источник правды)
                         flags · events · targets · exploit_health · meta
                          ▲        ▲          ▲         ▲         ▲
       пишет флаги  ──────┘        │          │         │         │
   ┌───────────────┐               │          │         │         │
   │ COLLECTORS    │  attack-data  │          │         │         │
   │ (пул воркеров)│◄──────────────┤          │         │         │
   │ эксплойты ×   │               │          │         │         │
   │ team×svc×fid  │        ┌──────────────┐   │         │         │
   │ жёсткий t/o,  │        │ ATTACK-DATA  │   │         │         │
   │ hot-reload,   │        │ poller       │   │         │         │
   │ карантин      │        │ cache last-ok│   │         │         │
   └───────────────┘        └──────────────┘   │         │         │
                                                │         │         │
   ┌───────────────┐   берёт pending, сдаёт     │         │         │
   │ SUBMITTER     │───────────────────────────┘         │         │
   │ token-bucket, │   пишет вердикты                      │         │
   │ AIMD-автотемп,│                                       │         │
   │ батчи, бэкофф │                                       │         │
   └───────────────┘                                       │         │
                                                            │         │
   ┌───────────────┐   читает всё, пишет runtime-команды    │         │
   │ GUI / CONTROL │◄──────────────────────────────────────┘         │
   │ http.server   │   pause/resume, enable/disable, темп,            │
   │ localhost-only│   reload эксплойта, калибровка вердикта  ─────────┘
   └───────────────┘
            ▲
            │ (опц., фаза 5) HTTP /push: тиммейты льют украденные флаги в общий сабмиттер
   ┌───────────────┐
   │ TEAM CLIENTS  │
   └───────────────┘
```

Процессная модель по умолчанию — **один процесс, несколько потоков** (collectors-пул,
submitter-поток, attack-data-поток, GUI-поток). Это проще и надёжнее для соло. Клиент-сервер
(§3.9) — опциональная надстройка той же БД/сабмиттера.

### Предлагаемая раскладка файлов (в той же `farm/`, совместимо)

```
farm/
  farm.py          # entry: поднимает engine + GUI; сохраняет CLI v1 (--once/--loop/--dry-run/...)
  engine.py        # оркестратор: запускает потоки, владеет жизненным циклом, graceful stop
  collectors.py    # пул эксплойтов: жёсткие таймауты, hot-reload, health/карантин (бывш. runner.work)
  submitter.py     # submit-loop: token-bucket, AIMD, батчи, бэкофф (бывш. submitters + _submit_pending)
  verdicts.py      # классификация вердикта + калибровка (выделено из submitters)
  attackdata.py    # + кеш last-good + свой цикл опроса
  targets.py       # + health/cooldown целей
  store.py         # схема v2: flags(+ttl,next_try,tries) · events · targets · exploit_health · meta
  runtime.py       # живое изменяемое состояние (enabled/paused/темп) — GUI пишет, циклы читают
  config.py        # как в v1 + новые необязательные ключи (дефолты безопасны)
  config.forcad.py # боевой пресет + новые ключи
  webgui/
    server.py      # http.server: дашборд + control-API, bind 127.0.0.1
    assets.py      # инлайновый HTML/CSS/JS одной строкой (офлайн, без CDN)
  util.py
  sploits/         # без изменений, интерфейс заморожен
# runner.py — остаётся тонким шимом на collectors+submitter ради старых импортов, затем удаляем
```

## 3. Компоненты

### 3.1 Engine (оркестратор) — `engine.py`
- Поднимает и останавливает потоки: attack-data poller, collectors-пул (по тикам раунда),
  submitter-loop, GUI-сервер.
- Владеет graceful shutdown: SIGINT/SIGTERM → «доработать текущий раунд, слить очередь по
  возможности, закрыть БД». `--once` = один проход коллекторов + одна попытка слить очередь.
- Единая точка, куда стекаются исключения потоков (поток не умирает молча — пишет `event`
  уровня ERROR и перезапускается с бэкоффом).
- Режимы: `--loop` (всё крутится), `--once` (один цикл), `--dry-run` (коллекторы + очередь,
  сабмиттер в no-op), `--no-gui` (без веб-морды), `--gui-only` (подключиться к живой БД и
  только смотреть/управлять — полезно тиммейту).

### 3.2 Flag store v2 — `store.py`
Состояния флага (конечный автомат):
```
NEW ──(украден, прошёл regex, не дубль)──► QUEUED
QUEUED ──(сабмиттер взял)──► INFLIGHT
INFLIGHT ──accepted──► ACCEPTED   (терминально, в счёт очков)
INFLIGHT ──drop──────► REJECTED   (invalid/own/too_old/duplicate — терминально)
INFLIGHT ──resubmit/unknown──► QUEUED  (next_try = now + backoff, tries++)
QUEUED/INFLIGHT ──(возраст > TTL или tries > max)──► EXPIRED  (терминально, больше не шлём)
```
Схема (ключевые поля):
```sql
flags(
  flag TEXT PRIMARY KEY,
  status TEXT,              -- QUEUED|INFLIGHT|ACCEPTED|REJECTED|EXPIRED
  service TEXT, target TEXT, flag_id TEXT,
  tries INTEGER DEFAULT 0,
  first REAL, last REAL,    -- когда украден / последняя попытка
  next_try REAL DEFAULT 0,  -- не трогать раньше этого времени (backoff)
  verdict TEXT              -- последнее сырое слово жюри (для дебага/калибровки)
)
-- индексы: (status, next_try), (service, target), (first)
events(ts REAL, level TEXT, kind TEXT, msg TEXT, data TEXT)   -- лента для GUI
targets(name TEXT PRIMARY KEY, host TEXT, up INTEGER, last_seen REAL, cooldown_until REAL,
        stolen INTEGER, accepted INTEGER)
exploit_health(service TEXT PRIMARY KEY, enabled INTEGER, runs INTEGER, errors INTEGER,
        last_ok REAL, last_err TEXT, avg_ms REAL, quarantined_until REAL)
meta(key TEXT PRIMARY KEY, value TEXT)   -- runtime: paused, rate, learned flags/min, ...
```
Надёжность:
- **WAL-режим** (`PRAGMA journal_mode=WAL`) — конкурентные чтения GUI не блокируют запись.
- **Батч-дедуп:** коллектор отбирает дубли одним `SELECT ... WHERE flag IN (...)` на пачку, а
  не вызовом `known()` на каждый флаг под локом (устраняет слабое место v1 #14).
- **TTL** берётся из `flag_lifetime_seconds` (ForcAD: `FLAG_LIFETIME_TICKS × round`). Флаг,
  живущий дольше, авто-`EXPIRED` — не занимает лимит сдачи.
- Все переходы — транзакционно; `INSERT OR IGNORE` сохраняет идемпотентность.

### 3.3 Collectors (пул эксплойтов) — `collectors.py`
- Строит задания `team × service × flag_id` (как v1), но:
  - **Жёсткий таймаут:** каждый `exploit()` исполняется с `future.result(timeout=hard_t)`;
    по таймауту воркер освобождается, эксплойту ставится ошибка (зависший поток-демон
    отпускается на произвол — не держит пул). Опционально (`isolation="subprocess"`) —
    запуск эксплойта отдельным процессом с `kill` по таймауту (защита от segfault/утечек в
    pwn-эксплойтах; дороже, включается на сервис точечно).
  - **Hot-reload:** модуль эксплойта перечитывается, если изменился `mtime` файла, либо по
    кнопке «reload» в GUI. Писать эксплойт в игре → ферма подхватывает без рестарта.
  - **Health/карантин:** на сервис копится runs/errors/avg_ms. Если доля ошибок > порога на
    N раундов подряд — эксплойт уходит в **карантин** (`quarantined_until`), в GUI горит
    красным; периодически авто-пробуем снова. Это «умное» самолечение, не тихий отказ:
    факт карантина — заметное событие.
  - **Cooldown целей:** недоступная цель (connect/timeout на всех сервисах) уходит в cooldown,
    воркеры её не долбят; периодический ре-пробинг.
- Отобранные флаги (regex ok, не дубль) → `store` как `QUEUED`, событие `+ svc team fid→flag`.

### 3.4 Attack-data — `attackdata.py`
- Отдельный поток опрашивает endpoint на своей частоте (`attackdata.poll_seconds`, по
  умолчанию = round).
- **Кеш last-good:** успешный ответ кладётся в `meta`/память; при сбое фетча коллекторы
  используют последний удачный снимок (слабое место v1 #8). Возраст кеша виден в GUI.
- Пресеты нормализации (teamservice / forcad / custom-hook) — как в v1, формат на выходе
  `{target_key: {service: [flag_id...]}}`.
- Защита: если endpoint отдаёт мусор/HTML (жюри перезагрузилось) — не роняем кеш, логируем.

### 3.5 Submitter — `submitter.py`
- **Отдельный поток-loop**, независимый от раундов. Берёт из `store` до `flags_per_submit`
  флагов в состоянии `QUEUED` с `next_try <= now`, шлёт батчем, разбирает вердикты, пишет
  переходы состояний.
- **Token-bucket rate-limit:** лимит жюри обычно задан как «N флагов в минуту» и «≤ M флагов
  за запрос». Бакет уважает оба; `min_seconds_between_submits` как fallback.
- **AIMD-автотюнинг темпа (умное):** старт с консервативного `flags_per_min`; пока нет сигналов
  rate-limit — аддитивно поднимаем; поймали `resubmit/too fast/rate-limit` — мультипликативно
  сбрасываем. Ферма сама нащупывает реальный потолок жюри. Выученное значение — в `meta`,
  видно и редактируемо в GUI.
- **Порядок сдачи:** по умолчанию newest-first (свежие флаги дальше всего от TTL — выше шанс
  accept), настраивается; у края бакета приоритет свежим. Протухающие (близко к TTL) можно
  поднимать в приоритете, чтобы успеть сдать до TOO_OLD.
- **Глобальный бэкофф:** вердикт «game not started / paused / over» по многим флагам → не
  переводим флаги в drop, а ставим **паузу сдачи** на `backoff` и ждём (слабое место v1 #15).
- Транспорты HTTP (POST/PUT, JSON/newline, token-header) и TCP (greeting/token/batch) — как в
  v1, вынесены без изменения семантики.

### 3.6 Verdicts — `verdicts.py`
- Классы: `accepted | drop | resubmit | unknown`.
- **ForcAD точно:** ответ `/flags` — JSON-массив объектов `{"flag","msg","status":bool}`. Если
  есть булев `status` — используем его (`true→accepted`), а при `false` смотрим `msg`, чтобы
  отличить `drop` (invalid/own/too old/already) от `resubmit` (game not started/too fast).
  Regex остаются fallback'ом для платформ без `status`.
- **`unknown` безопасно:** пустой/битый ответ → флаг остаётся `QUEUED` с backoff, но под
  лимитом попыток и TTL (не вечный ресабмит, слабое место v1 #12).
- **Калибровка из GUI:** кнопка «показать сырой ответ жюри на пробную пачку» → подсветить, как
  текущие regex его разбирают → поправить `verdicts.*` на лету. Снимает риск неверной
  классификации из-за непредвиденной формулировки жюри.

### 3.7 Runtime-state и конфиг — `runtime.py` + `config*.py`
- `config.py` читается на старте (как v1) и даёт **дефолты**. Все новые ключи необязательны.
- `runtime.py` — живой слой поверх конфига в `meta`-таблице: `paused`, включённость
  сервисов/эксплойтов/целей, темп сдачи, порядок, round_seconds. GUI пишет сюда, циклы
  читают каждую итерацию → изменения применяются **без рестарта** (слабые места v1 #10/#11).
- Hot-reload конфиг-файла — только для безопасного подмножества (темп/round/вердикты/вкл-выкл);
  смена структурных вещей (targets mode, submitter transport) — через рестарт, чтобы не ловить
  несогласованное состояние в середине раунда.
- Приоритет: `runtime (GUI)` > `config.local.py`/`config.prod.py` > `config.py`.

### 3.8 GUI / Control — `webgui/server.py`
- **Стек:** stdlib `http.server` + `ThreadingHTTPServer`. Одна самодостаточная HTML-страница,
  CSS/JS инлайном (без CDN — офлайн-бокс). Данные — короткий polling `/api/*` (1–2 c) или SSE.
- **Bind только `127.0.0.1`** (по умолчанию). Для доступа тиммейтам — явный `--gui-host` +
  токен в заголовке/Cookie (не светить управление фермой в игровой сети без аутентификации).
- **Read-only никогда не мутирует игру;** все мутации — только POST с токеном.

Экраны/панели:
1. **Dashboard:** статус (RUNNING/PAUSED), uptime, номер раунда, здоровье жюри и attack-data
   (возраст кеша), токен (маскирован). KPI-плитки: accepted всего, accepted/мин (5 мин),
   глубина очереди, dropped, expired, украдено за последний раунд. Мини-график accepted во
   времени и распределение вердиктов (инлайновый canvas).
2. **Flags:** таблица с фильтрами (статус/сервис/цель), поиск по флагу, возраст, попытки,
   последний вердикт. Экшены: «сдать сейчас», «пометить expired».
3. **Exploits:** по сервису — enabled, runs/errors/avg_ms, last_ok/last_err, карантин.
   Кнопки: enable/disable, **reload**, «прогнать сейчас» по одной цели (дебаг).
4. **Targets:** up/down, last_seen, cooldown, украдено/принято по каждой. Кнопки enable/disable.
5. **Submitter:** текущий/выученный flags/min, размер батча, токены бакета, «до след. сдачи N c»,
   пауза сдачи. Кнопка **калибровки вердикта** (сырой ответ + разбор).
6. **Config/Log:** живой лог (tail из `events`), редактор безопасного подмножества конфига,
   большая кнопка **PAUSE ALL / RESUME**.

Control-API (POST, токен):
```
/api/stats /api/flags /api/events /api/exploits /api/targets /api/submitter   (GET)
/api/control/pause | /resume
/api/control/service/<svc>/enable | /disable
/api/control/exploit/<svc>/enable | /disable | /reload | /run-now?target=...
/api/control/target/<name>/enable | /disable
/api/control/rate            {flags_per_min, per_submit, order}
/api/submitter/test          (пробная сдача/калибровка; в dry не шлёт реально)
/api/config (GET/POST безопасного подмножества)
```

### 3.9 Team client/server (опционально, фаза 5)
- **Server** = та же ферма: добавляет `POST /push` (токен), куда тиммейты льют украденные
  флаги. Сервер централизованно дедупит и сдаёт (один токен, один лимит — нет двойной сдачи и
  гонок за rate-limit). Модель как у DestructiveFarm (клиенты воруют, сервер сдаёт).
- **Client** = тонкий скрипт: гоняет локально свои эксплойты и `POST /push` флаги на сервер.
  Не нуждается в токене жюри, не знает про лимиты.
- Включается только если решим играть «общим котлом». Для соло не нужен.

### 3.10 Логи, метрики, события — `util.py` + `store.events`
- Текстовый лог (`farm.log`) как в v1 **плюс** структурные события в `events` (лента для GUI).
- Ротация `farm.log` по размеру (не забить диск — это тоже SLA-риск).
- Метрики считаются из `flags`/`events` (accepted/мин, доли вердиктов, health) — отдельной
  TSDB не заводим, SQLite достаточно для масштаба (десятки тысяч флагов).

## 4. Матрица отказов (максимальная безотказность)

| Сбой | Поведение v2 | Почему безопасно |
|---|---|---|
| attack-data endpoint лёг / отдаёт мусор | коллекторы на кеше last-good; возраст кеша в GUI | не прекращаем атаку, не роняем кеш |
| жюри `/flags` недоступно / 5xx | флаги остаются `QUEUED`, backoff сдачи | ничего не теряем, не спамим |
| жюри «game not started/paused» | глобальная пауза сдачи, флаги ждут | не жжём попытки/лимит зря |
| rate-limit от жюри | AIMD сбрасывает темп, token-bucket держит | сам находит потолок, без бана |
| эксплойт завис | жёсткий таймаут future (+опц. kill subprocess) | воркер-пул не деградирует |
| эксплойт стабильно падает | карантин + заметное событие, авто-ре-пробы | не тащит пул, видно в GUI |
| цель down | cooldown + ре-пробинг | не долбим мёртвую цель |
| процесс/бокс упал, Ctrl+C | SQLite WAL, состояние на диске, resume | очередь цела, нет пересдачи |
| флаг протух (TTL) | авто-`EXPIRED`, снят со сдачи | не жжём лимит на мёртвые флаги |
| битый/пустой ответ жюри | `unknown` → backoff под лимитом попыток | не вечный ресабмит, не дубли |
| diск заполняется логом | ротация `farm.log` | бокс не падает по диску |
| теряем связь с GUI | игра идёт в фоне независимо | GUI — наблюдатель, не критичный путь |

## 7. План внедрения (фазами, каждая — отдельно рабочая)

- **Фаза 0 — рефактор ядра (без смены поведения).** Разнести `runner.py` на `engine.py` +
  `collectors.py` + `submitter.py`; `store.py` → схема v2 (конечный автомат, индексы, WAL);
  вынести `verdicts.py`. На выходе ферма ведёт себя как v1, но внутри — развязанные циклы.
- **Фаза 1 — безотказность.** Decoupled submit-loop; TTL + retry/backoff; attack-data кеш
  last-good; жёсткий таймаут эксплойта; token-bucket. Это закрывает большинство слабых мест.
- **Фаза 2 — GUI read-only.** `http.server` дашборд: KPI, flags, exploits, targets, submitter,
  лента событий. Только наблюдение.
- **Фаза 3 — GUI-контролы.** pause/resume, enable/disable сервис/эксплойт/цель, смена темпа,
  калибровка вердикта, reload эксплойта, runtime-state в `meta`.
- **Фаза 4 — ум.** AIMD-автотюнинг темпа; карантин эксплойтов; cooldown/ре-пробинг целей;
  hot-reload по mtime; (опц.) subprocess-изоляция эксплойтов.
- **Фаза 5 — команда (опционально).** `POST /push` + тонкий клиент для тиммейтов.

Каждую фазу можно гонять на локальном стенде (`python run_local.py` + ферма) ещё до тест-дня.
