Я (Claude) работаю в **изолированном облачном контейнере**, а **не на вашем сервере**.
Проверено сырыми сокетами в обход прокси:

| скрипты деплоя/выгрузки | `deploy.sh`, `wg-multi`, `trafmon`, `filter_proxy` |

## 1. Что такое ForcAD и как устроена «вся инфраструктура»

ForcAD (github.com/pomo-mondreganto/ForcAD) — чистый на Python движок Attack-Defence,
разворачивается в Docker. Компоненты (из wiki/README проекта):

| Компонент | Роль |
|---|---|
| **celerybeat** | каждый раунд шлёт «round start» в Celery |
| **celery** (+ **flower**) | распределённо гоняет чекеры по всем парам команда×сервис (≈1 инстанс на 60 пар) |
| **checkers** | Hackerdom-совместимые скрипты: `check` (жив ли сервис), `put` (кладёт флаг), `get` (достаёт флаг). Запускаются от `nobody`, лежат в `checkers/<task>/` |
| **flag receivers** | приём украденных флагов: **TCP** (eventlet, `:31337`) и **HTTP** (Hackerdom, `PUT`, батч ≤100) |
| **client_api / admin_api** | данные для фронта (Vue); admin_api держит внутреннюю авторизацию |
| **events** | Socket.io — живые события/перезагрузка скорборда |
| **monitoring** | Prometheus-экспортёр, метрики флагов на `/api/metrics` |
| **redis / postgres / rabbitmq** | кеш «существует ли флаг» / персист игры / брокер Celery |
| **nginx** | единственный внешний вход, load-balance + rate-limit приёмников флагов |
| **initializer** | ждёт БД, инициализирует схему; правки конфига на ходу — через admin-панель |
| **scoreboard** | Vue-фронт на `:8080`, админка `/admin/`, flower `/flower/` |

### Сетевая карта (из правил 2026 / RECON.md)

```
                 ┌─────────────────────────────────────────┐
  WireGuard VPN  │  Игровой сервер / скорборд               │
  (организаторы) │  http://10.10.10.10      (внутри VPN)    │
       │         │  https://GAME_HOST       (из интернета)  │
       │         │  attack_data · /flags · /admin · :31337  │
       ▼         └───────────────▲──────────────────────────┘
 ┌──────────┐ ┌──────────┐       │ submit (твой токен)
 │ 10.60.1.2│ │ 10.60.2.2│  ...  │
 │  (наш?)  │ │  (враг)  │       │  ← чекер каждый раунд ходит
 │ сервисы  │ │ сервисы  │          put/get/check на КАЖДЫЙ бокс
 └──────────┘ └──────────┘
   боксы команд 10.60.N.2 (N=1..10), на каждом один и тот же набор уязвимых сервисов
```

### Жизненный цикл раунда и флага

- Раунд = **60 с** (правила 2026). Флаг живёт **10 раундов = 600 с**, потом `too old`.
- Каждый раунд чекер на КАЖДЫЙ бокс: `put` свежий флаг → позже `get` (достаётся ли легально) → `check` (протокол жив). Статус = худший; `SLA%` = доля UP-раундов.
- Формат флага: `[A-Z0-9]{31}=` (32 символа; в ForcAD первый символ часто = первая буква сервиса).
- **flag_id** (публичный id места флага) выдаётся атакующим через attack_data. Его генерят
  чекеры типа **`pfr`** (public flag data) ; тип **`nfr`** означает, что `flag_id` передаётся
  в `get`. Семантика flag_id зависит от сервиса (имя юзера / id записи / `user/key` и т.п.).

### Где живут уязвимые сервисы и что реально можно «выгрузить»

- Уязвимые сервисы кастомные под соревнование и крутятся **на боксах команд** `10.60.N.2`.
  В этом репозитории их **нет** (здесь только тренировочный baseline из 3 сервисов).
- **Наш бокс** (где у нас root и VPN) — единственное место, где можно взять **исходники**
  (обычно docker-compose + код сервисов, что раздали организаторы). С чужих боксов —
  только сетевой интерфейс (чёрный ящик).
- Поэтому «выгрузить инфраструктуру» = с нашего бокса снять: attack_data, список
  сервисов+портов, docker-состояние и исходники сервисов. Это делает `recon/collect_infra.sh`.

## 2. Контракт интерфейсов (с чем работает ферма)

### attack_data (публичные flag_id целей)

```
GET http://10.10.10.10/api/client/attack_data           (или https://GAME_HOST/...)
-> { "<service>": { "10.60.X.2": ["flag_id1","flag_id2", ...], ... }, ... }
```

Парсер `forcad` в [farm/attackdata.py](farm/attackdata.py) уже нормализует этот вид в
`{team_ip: {service: [flag_id,...]}}` и **кеширует last-good** (упал фетч → бьём по
последнему снимку, а не по пустоте).

### Сдача флагов — у ForcAD ДВА приёмника, наш submitter умеет оба

1. **HTTP** (Hackerdom): `PUT /flags`, токен в заголовке, тело — JSON-массив, батч ≤100.
   ⚠️ В исходниках ForcAD заголовок называется **`X-TeamToken`**, а в правилах/нашем
   пресете — **`X-Team-Token`**. **Проверить в день Х** (см. таблицу расхождений ниже).
2. **TCP**: `:31337`, первой строкой — токен, затем флаги построчно.

[farm/submitter.py](farm/submitter.py) поддерживает оба (`mode: http` / `mode: tcp`,
`send_token_first`, `batch`, `token_header`). [farm/verdicts.py](farm/verdicts.py)
разбирает ForcAD-ответ (список `{"flag","msg","status":bool}` — `status` авторитетен)
на классы accepted / drop / resubmit.

### ⚠️ Расхождения источников — ПРОВЕРИТЬ в день Х (по 2-3 ручным запросам)

| Что | Варианты | Как проверить |
|---|---|---|
| путь attack_data | `/api/client/attack_data` vs `/api/attack_data` | `curl http://10.10.10.10/api/client/attack_data` |
| транспорт сдачи | HTTP `PUT /flags` vs TCP `:31337` | что указано в правилах/у жюри; оба готовы в submitter |
| заголовок токена | `X-Team-Token` vs `X-TeamToken` | сдать 1 тестовый флаг, посмотреть вердикт |
| формат флага | `[A-Z0-9]{31}=` (возможна привязка 1-й буквы к сервису) | взять любой flag_id-флаг из `get` |
| порты сервисов | публикуют перед стартом | `collect_infra.sh` + объявление жюри |

## 3. Наша ферма: как она ложится на ForcAD

Пресет [farm/config.forcad.py](farm/config.forcad.py) уже синхронизирован с правилами 2026
(10.60.N.2, раунд 60 с, флаг 600 с, парсер forcad, submit PUT /flags). Боевой конфиг —
[deploy/config.prod.example.py](deploy/config.prod.example.py) → `farm/config.prod.py`
(gitignored), который наследует forcad-пресет и переопределяет только 3 секрета:

1. `targets.my_team_ip = 10.60.<НАШ_ID>.2` — свой бокс (никогда не атакуем);
2. `services = {"<имя>": <порт>, ...}` — реальные сервисы и порты;
3. `submitter.token = <НАШ_ТОКЕН>` (+ при only-HTTPS: `url` на `https://GAME_HOST/...`).

Режимы [farm/farm.py](farm/farm.py):

```bash
python farm/farm.py --config farm/config.prod.py --once --dry-run   # украсть+очередь, НЕ сдавать (безопасная проверка)
python farm/farm.py --config farm/config.prod.py --loop             # воровать+сдавать в цикле, GUI :8070
python farm/farm.py --config farm/config.prod.py --loop --service X # только один сервис
python farm/farm.py --config farm/config.prod.py --once  --team teamN
python farm/farm.py --config farm/config.prod.py --loop --no-gui    # headless (на сервере)
```

Умные части (всё уже внутри): **AIMD-автотюнинг** темпа сдачи (сам ищет лимит жюри),
конечный автомат флага `QUEUED→INFLIGHT→ACCEPTED/REJECTED/EXPIRED` с TTL+бэкоффом,
**карантин** сломанных эксплойтов, **cooldown** мёртвых целей, **hot-reload** по mtime,
SQLite WAL + resume. **GUI** `http://127.0.0.1:8070` — KPI/вердикты/здоровье/контролы на лету.
**Командный режим**: тиммейты запускают [farm/client.py](farm/client.py) и пушат флаги в нашу
ферму (`POST /push`, общий дедуп/лимит).

### Эксплойт = плагин

Один файл `farm/sploits/<service>.py` с **замороженным** интерфейсом:

```python
def exploit(host: str, port: int, flag_id) -> list[str]:
    # вернуть список украденных флагов; [] если не нашли. flag_id может быть None.
    # ТОЛЬКО сетевой интерфейс сервиса; свои таймауты 5-7с; без sys.exit/утечки исключений.
```

Эталоны (тот же интерфейс): `services/{web,crypto,depot}/sploit.py`. Шаблон промпта на
написание — [farm/EXPLOIT_PROMPT_TEMPLATE.md](farm/EXPLOIT_PROMPT_TEMPLATE.md).

### Мульти-VPN (атака через все тоннели сразу)

[deploy/wg-multi/wg-multi.sh](deploy/wg-multi/wg-multi.sh) поднимает каждый `*.conf` в
**своей** таблице маршрутов (policy-routing, не конфликтует с основным VPN) и пишет
`FARM_VPN_MARKS`. [farm/vpn_balance.py](farm/vpn_balance.py) по кругу метит исходящие сокеты
`SO_MARK` — каждая атака уходит другим тоннелем. Нужен root/CAP_NET_ADMIN (на боксе ферма
от root — просто работает; иначе тихо деградирует в один маршрут). Эксплойты не меняются.

## 4. Атака — пошагово в день Х

1. На сервере поднять VPN, убедиться что видно `10.10.10.10` и соседей (`wg test`).
2. `collect_infra.sh` → attack_data, список сервисов, порты, исходники с нашего бокса.
3. Заполнить `farm/config.prod.py` (ID, токен, порты) — см. §3.
4. На КАЖДЫЙ сервис — эксплойт в `farm/sploits/<service>.py` (по исходнику; промпт-шаблон).
   Быстрая проверка отдельного файла: `python farm/sploits/<svc>.py <host> <port> <flag_id>`.
5. Холостой прогон: `farm.py --config farm/config.prod.py --once --dry-run` — цели парсятся,
   эксплойты воруют, в очередь кладётся, **ничего не сдаётся**.
6. Боевой: `farm.py --config farm/config.prod.py --loop` (на сервере — `--no-gui`, дашборд
   через SSH-тоннель). Следить за accepted/вердиктами на `:8070`.

## 5. Защита — патч-луп без потери SLA

Правило: закрыть у себя ту же дыру, **не уронив то, что проверяет чекер**. Инструменты
([defense/README.md](defense/README.md)):

- **[defense/verify.py](defense/verify.py)** — кладёт флаг чекером, проверяет `put/get/check`
  (SLA) и гоняет эталонный эксплойт. Цель: `SLA OK + VULN blocked` = **GOOD PATCH**.
  Боевой режим: `python defense/verify.py <svc> 10.60.<НАШ_ID>.2 <порт>`.
- **[defense/trafmon.py](defense/trafmon.py)** — по pcap находит, **какой входящий запрос
  вызвал выдачу флага** (это чужой эксплойт): чиним именно его, а запрос **переигрываем в
  атаку** против других. `--save-exploits` сохраняет байты.
- **[defense/filter_proxy.py](defense/filter_proxy.py)** — быстрый митигейт: режет узкую
  сигнатуру payload'а перед сервисом (HTTP и сырой TCP), пока нет полного патча. Держать
  сигнатуры узкими, следить за SLA.

Нельзя «защищаться» фаерволом по IP: к сервисам ходит и чекер, и соперники — заблокируешь
чекер → упадёт SLA. Основная защита = **правильный патч** + `verify.py`.

## 6. Деплой на боевой сервер

С ПК (Git Bash), [deploy/README.md](deploy/README.md) / [deploy/deploy.sh](deploy/deploy.sh):

```bash
cp deploy/deploy.env.example deploy/deploy.env        # адрес/юзер/ssh-ключ сервера
cp deploy/config.prod.example.py farm/config.prod.py  # наш IP, токен, порты сервисов
./deploy/deploy.sh all          # залить код + зависимости + systemd-юнит ad-ctf-farm
# положить *.conf организаторов в deploy/wg-multi/conf/, затем:
./deploy/deploy.sh wg-push      # залить конфиги в /etc/ad-ctf/wg
./deploy/deploy.sh wg up        # поднять ВСЕ тоннели (каждый в своей таблице)
./deploy/deploy.sh wg test      # 10.10.10.10 виден через каждый тоннель
./deploy/deploy.sh start        # запустить ферму (подхватит FARM_VPN_MARKS)
./deploy/deploy.sh status|logs  # статус/живой лог
```

Дашборд — через SSH-тоннель на `127.0.0.1:<DASHBOARD_PORT>` (control-API наружу не торчит).
Без systemd — запуск вручную в tmux (см. deploy/README «Без systemd»).

## 8. Поиск уязвимостей — методика и разведка прошлого года

Типовые классы по типу сервиса (из [RECON.md](RECON.md) / EXPLOIT_PROMPT_TEMPLATE):

- **web**: SQLi/NoSQLi, IDOR (угадываемые id), обход авторизации, SSTI, path traversal,
  небезопасная десериализация, слабые/предсказуемые токены сессий.
- **crypto**: ECB / повтор гаммы (two-time pad), повтор nonce, предсказуемый seed/ключ,
  length-extension, слабый подписывающий секрет (брут), публично выставленный ciphertext,
  самодельные подписи (WOTS без контрольной суммы / с переиспользованием ключа).
- **pwn**: переполнение буфера / формат-строка / off-by-one / логика; цель — заставить
  сервис отдать чужую запись/память. Обычно сырой сокет + заранее собранный payload.

Разведка прошлого года (баги часто повторяются): сервисы `workflow` (2 уязв.), `zounds` (2),
`secretscribble` (3). Под эти имена уже есть заготовки в `config.forcad.py → sploit_paths`.

- **secretscribble** (WOTS-кука): эксплойт прошлого года **готов и проверен** —
  [farm/sploits/secretscribble.py](farm/sploits/secretscribble.py) (подделка сессионной
  куки: один глобальный WOTS-ключ без контрольной суммы). Если сервис тот же — заново не писать.
  Исходники разведки: `recon/2024_sploits/sploit_{1,2,3}.py`.
- **zounds** (защита): агрессивный файловый «клинер» сносит флаги раньше чекера → падает SLA.
  Защита — замедлить/отключить клинер (но не дать файлам забить диск).

Тренировочные эталоны (тот же интерфейс эксплойта) — `services/{web,crypto,depot}/`:
SQLi (UNION), повтор гаммы AES-CTR, path traversal. Полезны как «калибровка» фермы/защиты.

## 9. Что мне прислать, чтобы я начал писать эксплойты/патчи под реальные сервисы

Запусти на сервере (внутри VPN) и пришли результат:

```bash
# на боевом сервере, из корня репо:
bash recon/collect_infra.sh                 # по умолчанию http://10.10.10.10
# или если только HTTPS:  bash recon/collect_infra.sh https://GAME_HOST
```

Он сложит всё в `recon/out/` и соберёт `recon/out/infra_bundle.tar.gz`. Пришли мне (вставь
в чат или scp/загрузи):

1. **attack_data** (`recon/out/attack_data.json`) — имена сервисов, цели, примеры flag_id.
2. **Список сервисов + порты** (`recon/out/ports.txt`, `services.txt`) — что на каком порту.
3. **Исходники сервисов** с нашего бокса (`recon/out/sources/…` или сам tar) — главное: по
   одному сервису это **код `app`/бинарь + описание протокола/эндпоинтов** и **пример flag_id
   и что он значит** (имя юзера / id записи / user/key / …).
4. Любые 1-2 примера живого обмена (сырой запрос-ответ `curl`/`nc`) — ускоряет разбор.

Как только это будет — пишу на каждый сервис эксплойт под интерфейс фермы (`farm/sploits/`)
и патч под защиту (`services/<svc>/app.py`-стиль + проверка логикой `verify.py`), по отдельной
задаче на сервис, с разбором «в чём дыра».
